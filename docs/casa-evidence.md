# CASA (ADA-CASA AL1) evidence map — Tartly

Last updated: 31 October 2026<br>
Assessment due: **28 January 2027** (Google OAuth verification, project `1092559907127`)<br>
Required level: **AL1 (formerly Tier 2)** — developer self-assessment with evidence,
reviewed by an ADA-authorized lab. All CASA requirements apply; the lab does not
re-run tests against the app.

Source of truth for requirements: [ADA CASA Specification v2.1.1](https://github.com/appdefensealliance/ASA-WG/blob/main/CASA/CASA%20Specification.md)
and the [CASA Test Guide](https://github.com/appdefensealliance/ASA-WG/blob/main/CASA/CASA%20Test%20Guide.md).

## 0. How AL1 works

- You (the developer) fill in an evidence statement for every applicable CASA
  test case and hand the bundle to the lab.
- The lab reviews evidence against the requirements and issues a **Letter of
  Validation (LOV)**. Google sees the LOV and unblocks verification.
- AL2 would have the lab test the app directly (more expensive, Marketplace
  badge). Google assigned AL1; stay at AL1 unless you want the Marketplace
  badge.
- Annual recertification is required after approval.

## 1. Evidence index (requirement → proof)

### 1 Authentication

| Spec | Requirement | Evidence in repo / infra |
| --- | --- | --- |
| 1.1.1–1.1.3 | Password security | Tartly has **no password auth of its own**: users authenticate via Google/Microsoft OAuth through Better Auth (`lib/auth.ts`). Password storage is delegated to the IdP. Evidence: `lib/auth.ts`, consent screen config. Brute-force mitigation: Better Auth rate limit (`rateLimit` block, Redis-backed, 100/60s) + provider-side lockout. |
| 1.2.1 | No default accounts | No seeded/default user or admin accounts in `drizzle/` migrations or seed scripts. Evidence: migrations list + `scripts/`. |
| 1.3.1–1.3.4 | Out-of-band verifiers | OAuth `state` is generated by Better Auth and validated on callback (PKCE-capable authorization code flow). Email-based verification codes are not issued by Tartly. Evidence: `lib/auth.ts` (`storeStateStrategy: "cookie"`), onboarding connect flow. |

### 2 Session management

| Spec | Requirement | Evidence |
| --- | --- | --- |
| 2.1.1 | No auth material in URLs | OAuth tokens never appear in query strings; `state` only. Evidence: `lib/auth.ts`, `app/api/auth/[...all]/route.ts`. |
| 2.2.1 | Logout invalidates sessions | Better Auth `preserveSessionInDatabase: false`; sessions mirrored to PG and revoked on sign-out. Evidence: `lib/auth.ts` session block, `lib/session.ts`. |
| 2.2.2 | Terminate other sessions on password change | Delegated to Google/Microsoft (IdP password change revokes grants). Tartly's own session store is invalidated via `invalidateSessionUserCache` on user delete. Evidence: `lib/auth.ts` `databaseHooks.user.delete`. |
| 2.2.3 | Stateless tokens ≤ 24h | Cookie cache JWE, `maxAge: 5 * 60` (5 minutes). Evidence: `lib/auth.ts`. |
| 2.3.1–2.3.2 | Secure/HttpOnly cookies | Better Auth defaults set `Secure` + `HttpOnly` on session cookies in production. Evidence: `lib/auth.ts`, deployed response headers. |
| 2.3.3 | Session tokens over static keys | OAuth access/refresh tokens stored per-user in Better Auth `account` table; no static API keys for user auth. Evidence: `lib/db/schema.ts` (account table). |
| 2.3.4 | Tamper protection | JWE cookie cache + signed session token. Evidence: `lib/auth.ts`. |
| 2.4.1 | Re-auth for sensitive actions | Account deletion / disconnect / permanent delete require an authenticated session; permanent delete additionally requires explicit confirmation dialog. Evidence: `app/settings`, `lib/mail/service.ts` (deleteForever). |

## 2. Restricted-data handling (Google-specific, beyond CASA)

CASA is generic; Google's reviewers also check these. Already satisfied in repo
(see `docs/google-oauth-verification.md`):

- Tokens held by Better Auth, not app tables; Google calls centralized in
  `lib/gmail/*` and `lib/calendar/*`.
- Logs designed not to contain message bodies or tokens (redacting logger).
- Retention jobs delete event/send-ledger records on a schedule
  (`lib/email-operator/retention.ts`: 30-day event log, 90-day send ledger).
- Privacy policy discloses access, use, storage, sharing, protection, retention,
  deletion, Limited Use, and AI-training affirmation (`/privacy`).
- Account disconnect deletes tokens; full data deletion within 30 days, backups
  within 90 days (privacy policy §7–8).

## 3. Gaps to close before the assessment

These are the items most likely to fail AL1. Tackle in this order:

1. **Dependency audit** — run `npm audit` on the production tree and fix or
   document every high/critical. (6.1.1)
2. **TLS evidence** — run an SSL Labs scan of `tartly.in` and save the A/A+
   report. (4.1.1–4.1.2)
3. **DNS/subdomain audit** — export the `tartly.in` DNS zone, remove dangling
   CNAMEs, verify no takeover. (6.4.1)
4. **MFA on Cloud Console** — enable 2FA on the project owner account and any
   Editor; screenshot for evidence. (3.3.1)
5. **Admin surface** — confirm there is no internet-facing admin panel; if one
   is added later, gate it behind MFA first.
6. **Incident response runbook** — add `docs/runbooks/security-incident.md`
   covering detection, containment, token revocation, user notification, and
   post-mortem. (Not strictly a CASA line, but labs ask for it.)
7. **Data deletion evidence** — document the end-to-end deletion flow (disconnect
   → token delete → account delete → 30-day purge → 90-day backup expiry) and
   test it on a throwaway account; capture screenshots. (Google restricted-data
   requirement.)
8. **Architecture + data-flow diagrams** — one page each: components, trust
   boundaries, where Google tokens/data live, encryption, retention. Labs ask for
   these up front.
9. **Third-party/subprocessor list** — Vercel, Neon/Postgres, Upstash Redis,
   Cloudflare R2, ImageKit, OpenAI-compatible provider, Dodo Payments, Google,
   Microsoft. Include in the privacy policy and the evidence bundle.
10. **CASA accelerator** — if you hold any current cert (SOC 2, ISO 27001,
    PCI-DSS, etc.), hand it to the lab first; it can reduce the required checks.
